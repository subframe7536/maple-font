# CJK variable TrueType AutoHint

The opt-in backend uses conservative horizontal-edge alignment implemented in Maple with FontTools. The external candidates below were not selected. Both faces of the final hinted release-named archive were verified against a separate unhinted build from the same tag and settings.

## Reproduction baseline

Maple Mono `v8.0-beta.4` (`6d4ea0d1`), in a detached worktree on Windows. The release resolver and build pipeline route `--cjk-variable` to the merged variable outputs. `--cjk-hinted` controls the final static output, including the fallback path that instantiates temporary VFs; it does not hint the persisted VFs.

With the project environment installed from the existing lockfile (`uv sync --frozen --python 3.13`), the control build in the release worktree was:

```sh
uv run --frozen --no-sync build.py --ttf-only --least-styles --debug --cache --no-hinted --width slim --cjk cn --cjk-variable --nf --archive
```

Tools: uv 0.13.5, Python 3.13, fontmake 3.12.1, fontTools 4.63.0, Nerd Fonts 3.5.0. The build downloaded the CN variable base and validated it against the tag's expected digest. It produced `MapleMonoSLDebug-NF-CN-VF.zip`, containing upright and italic VFs, a build README, and the project's SIL Open Font License 1.1 as `LICENSE.txt`. ZIP CRC check passed. SHA-256: `0beeb9877aa01f1a219a559e5fc340d447324a508ce1e9962788ff48ebc60494`.

The control has 41,401/41,399 cmap entries (upright/italic), `wght` 100–800 with default 400, and no `cvt `, `cvar`, `fpgm`, or `prep` table in either VF. Using HarfBuzz 14.3.0 (uharfbuzz 0.56.0), `=>`, `!=`, and `->` substituted with `calt` enabled at all five tested weights in both faces. U+E0B0 and U+F120 mapped to the expected icon glyphs with 500-unit advances.

The default static-instance output also failed that fixture at 9 ppem; this error is not itself evidence of a variation-specific error.

The official, Microsoft-signed MSI was inspected without installing it. Its bundled `VTTShell -?` only exposes compilation and stripping, not automatic hint generation. The GUI autohinter was not tested; the compiler's MIT license does not establish the GUI license.

On a 266-glyph subset of the actual merged upright NF-CN VF, 120 composite definitions also differed at the FontTools object level. This was a prototype, not a proposed wholesale replacement of the original `glyf` table.

## Chlorophytum subset proof and rejection

FreeType 2.13.2 via freetype-py 2.5.1, grayscale, with runtime autohint and embedded bitmaps disabled. Native runs used `FT_LOAD_PEDANTIC`; the control used `FT_LOAD_NO_HINTING`. Compare each weight 100/400/450/700/800 at 9/10/12/14/16 ppem. On the instruction-only subset:

- `fvar`, `gvar`, `cmap`, `GSUB`, and `hmtx` were byte-identical. Unhinted outline points, advances, and grayscale bitmaps matched the original subset. FontTools evaluations at all five weights gave 1.0 em for sampled Han and 0.5 em for digits and the two sample icons.
- At each of the 25 weight–size pairs, 20 sampled Han bitmaps changed with native hints enabled (500 changes total). No pedantic interpreter error or hint-induced advance change occurred in the sampled set. Ordinary FreeType pixel advance rounding at 9 ppem also occurred in the unhinted font and was not counted as an error.
- A 4-connected component comparison at grayscale coverage 32/255 flagged 53 changes (a triage signal, not 53 proven defects). Direct bitmap inspection showed regressions worth addressing before integration: at 100/9 ppem the lower strokes of `永` ran together more readily; at 800/12 ppem the central joint in `字` lost the connected appearance of the control. The hints also sharpened some strokes, e.g. `三` at 100/9 ppem.
- The full upright Chlorophytum analysis reached roughly 6% after 2m38s with four workers (27,668 tasks). It was stopped because of the subset quality and preservation concerns. No full Chlorophytum-hinted face was produced.

## Selected backend: bounded native Y alignment

The built-in backend ([implementation](../scripts/font_ops/variable_hinting.py), revision 1) is original Maple code, using FontTools 4.63.0 (MIT) and the [OpenType TrueType instruction specification](https://learn.microsoft.com/en-us/typography/opentype/spec/tt_instructions). No external executable, third-party hint program, or package dependency is added. The font and generated archive remain under SIL OFL 1.1. The backend chooses one long horizontal edge per eligible simple Han glyph. At 9–20 ppem the native glyph program reads the anchor on the **current interpolated outline**, computes its distance to the nearest pixel, and translates all contours equally by at most 8/64 pixel. Phantom points, horizontal positions and relative outline geometry are unchanged. This is not stem-width or multi-stroke hinting. Composite glyphs, Han glyphs without a qualifying edge, and other scripts/icons are not instructed. A subset of real Maple outlines passed the native interpreter and uniform-shift checks before the complete build.

In the detached release worktree, first build the unmodified tag, retain its output separately, then apply the implementation and run the second command. `--cache` reused the matching base and Nerd Font stages but invalidated the merged CJK stage. The selected CN base digest was `1e809c55f551dd519d8429d12a0d2f77f9c7c4f9b133b310374a552137c853b6`.

```sh
uv sync --frozen --python 3.13
uv run --frozen --no-sync build.py --format ttf --least-styles --no-hinted --width slim --cjk cn --cjk-variable --nf --archive
uv run --frozen --no-sync build.py --format ttf --least-styles --cache --no-hinted --width slim --cjk cn --cjk-variable --cjk-vf-autohint --nf --archive
```

Actual build tools: uv 0.13.5, Python 3.13.15, FontMake 3.12.1, FontTools 4.63.0, Nerd Fonts 3.5.0. The hinted build completed in 84.62 seconds with the prerequisite stages cached. Both archives use the standard `MapleMonoSL-NF-CN-VF.zip` layout. The hinted ZIP passed a CRC check and its `LICENSE.txt` matched the tag's `OFL.txt` (ignoring line endings).

### Full archive verification

- FontTools comparison of the two packaged faces: only `glyf`, `loca`, `maxp`, and `head` differ. `fvar`, `gvar`, `cmap`, `GSUB`, and `hmtx` are byte-identical, and glyph order, contour coordinates and flags, and composite definitions are unchanged. Both preserve `wght` 100–800, default 400, and contain programs for 27,068 of 27,670 mapped Han glyphs.
- At all five weights in both faces, HarfBuzz 14.3.0 (uharfbuzz 0.56.0) preserved actual `calt` substitution for `=>`, `!=`, and `->`, and mapped U+E0B0 and U+F120 as in the control. Sampled Han advances were 1,000 units (1.0 em); digits and these icons were 500 units (0.5 em).
- In FreeType 2.13.2 (freetype-py 2.5.1), each weight 100/400/450/700/800 was compared at 8/9/10/12/14/16/20/21 ppem, with FreeType's auto-hinter and embedded bitmaps disabled. For 31 Han and 16 non-Han samples per face, the hint-off raster and outline matched the control; native hinting changed 29–31 Han bitmaps in every in-range weight–size pair (915 changes upright, 917 italic), and none at 8 or 21 ppem. Every sampled outline shift was uniform and vertical, no greater than 1/8 pixel. There was no advance-width change versus the equivalent control load. An additional pedantic sweep across all instructed glyphs in both faces at 9/12/16 ppem and all five weights completed 812,040 loads without an interpreter error.
- A 4-connected component screen at coverage 32/255 flagged 64 upright and 69 italic bitmap changes. A change in pixel sampling can cross this threshold even though every contour moves by exactly the same amount. Direct bitmap review of the earlier `永` (100/9) and `字` (800/12) regressions in both faces found no comparable new severe join or break; low-contrast details changed at other settings, e.g. `字` upright at 100/12. This does not establish universal visual improvement or the absence of rendering regressions in unsampled glyphs.
- Ruff format/lint, Pyrefly and 60 targeted tests passed. The full Windows suite ran 283 tests; its only error was the same pre-existing symbolic-link privilege failure (`WinError 1314`).

### DirectWrite follow-up

The two ZIPs above were re-checked by SHA-256 and loaded directly from extracted files through `IDWriteFactory6::CreateFontFaceReference`, without installing fonts or requesting simulated bold/italic. `IDWriteFontFace5::HasVariations` and `GetFontAxisValues` confirmed the requested `wght` for each face, and no-grid-fit masks of `三`, `永`, and `字` at 12 ppem differed across all five weights. The rasterizer was Windows 11 26H2 build 26300.9974, `dwrite.dll` 10.0.26100.8875.

At 96 DPI, the probe used [`IDWriteFactory3::CreateGlyphRunAnalysis`](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_3/nf-dwrite_3-idwritefactory3-createglyphrunanalysis) with an integer baseline origin and `CreateAlphaTexture` on each glyph. It compared 31 Han and 16 non-Han samples per face at 100/400/450/700/800 and 8/9/10/12/14/16/20/21 ppem. Both faces recommended Natural Symmetric rendering with grid fitting enabled throughout the grid. Explicit Natural Symmetric runs matched those recommendations byte for byte. The other distinct mode was DirectWrite's GDI Classic-compatible ClearType, not actual GDI.

- With grid fitting forced off, all control/hinted pairs were identical (11,280 comparisons across the three distinct profiles). With fitting enabled, recommended grayscale and ClearType each changed 1,826 Han masks (29–31 per in-range face/weight/size group). GDI Classic-compatible ClearType changed 1,759 (25–31 per group). All five weights showed effects. No 8/21 ppem or non-Han mask changed in any mode. Han design advances stayed at 1,000 units, digits and sampled icons at 500; both natural and GDI Classic-compatible widths matched the control.
- Direct inspection of six regression cases in both faces showed no clear new break or merge in `永` at 100/9 in the recommended profiles. At 800/12 the grayscale join in `字` lost contrast in both faces: a 4-connected mask threshold of 96/255 split it into two components after hinting, while it remained one at 64/255. At 100/12 in GDI Classic-compatible ClearType, the channel-averaged mask of `字` split at 16/255 and 32/255 in both faces; the enlarged proof shows a weaker thin join. This is a raster trade-off, not evidence of damaged font outlines or changed advances.
- The proof compared raw rasterizer coverage, not application-specific gamma/compositing, monitor settings, fractional origins, or all glyphs. Actual GDI and end-to-end editor rendering remain untested. The local comparison harness, per-glyph results, and enlarged masks are saved separately from the ZIP; no build code or package was changed for this follow-up.

#### Why the beta.4 static Hinted package lost bytecode

The [successful upstream build](https://github.com/subframe7536/maple-font/actions/runs/45039667714/job/137261138045) ran at `d6ef69ea` and logged both base TTF hinting and a downloaded static CN base. The relevant code is unchanged from the beta.4 tag. The static release step passes `--hinted` to choose the hinted NF base and label the resulting archive, but does not pass `--cjk-hinted`; the release config leaves `cjk.use_hinted` false, so it does not run a new hinter after the final merge.

During static CJK postprocessing, [`postprocess_cjk_extended_static_font`](../scripts/cjk/static.py) calls `remove_target_glyph(font, ".1")`. At the beta.4 tag, that [helper](../scripts/font_ops/opentype.py) always ran a FontTools subset with `hinting=False`, even if no glyph name matched. This removed every glyph program and the shared `cvt `, `fpgm`, and `prep` tables from the font, not just any deleted glyphs' instructions. It left the `head.flags` bits, which are not proof of executable hints.

A read-only reproduction fed the official `MapleMono-NF-Regular.ttf` from `MapleMono-NF.zip` (SHA-256 `a7cadf42241c0c0adc5cfcc0401ea92fc5f3f89b24a891aad6ee9dbf9b20512e`) through the release helper in memory. The input contained 1,806 instructed glyphs, all three global hint tables, and 53 bytes on the glyph for `0`. The helper produced zero instructed glyphs, no global hint tables, and no program for `0`, matching the published NF-CN Regular. Using a deliberately unmatched suffix still removed all programs. Re-running the same subset with only `hinting=True` preserved all 1,806 programs and the same three tables. No build code or archives were changed for this diagnosis.

The follow-up fix preserves hints during that subset and invalidates older hinted static CJK cache entries. A real Regular merge of the official NF input and digest-verified CN base retained all 1,453 cmap entries whose glyphs carried instructions, with byte-identical programs and `cvt `, `fpgm`, and `prep`. The unhinted NF input still produced no programs or shared hint tables. Both outputs retained the 41,401 code points of the corresponding beta.4 face. With FreeType native hinting at 9, 12, and 16 ppem, `0` and `A` rendered as in the hinted NF base, while the sampled Han glyphs `一` and `字` received no new instructions. This fix preserves existing base hints; it does not enable the separate final static AutoHint pass.

#### Inherited Powerline CVT error

On a single Regular face at 12 ppem, `FT_LOAD_PEDANTIC | FT_LOAD_NO_AUTOHINT | FT_LOAD_NO_BITMAP` reproducibly returns `0x86` (`Invalid_Reference`) for U+E0B0 in the official `MapleMono-TTF-AutoHint.zip` and `MapleMono-NF.zip` and the rebuilt NF-CN. They have identical five-point outlines, glyph programs, and shared hint tables for this case. The plain hinted TTF already fails, before any Nerd Font or CJK merge. The unhinted NF passes. Clearing only U+E0B0's program in a temporary in-memory copy restores a 9×17 bitmap with the shared tables left in place. FreeType 2.13.2 interpreter versions 35 and 40 both reject the original in strict mode.

A locally instrumented FreeType 2.13.2 build traced the first error to [`RCVT` (`0x45`)](https://github.com/freetype/freetype/blob/920c5502cc3ddda88f6c7d85ee834ac611bb11cc/src/truetype/ttinterp.c#L3086-L3105), in `fpgm` at byte 2895. The call chain is 23 → 21 → 139 → 78 → 77. It tries to read CVT index 117 from a 114-entry table (valid indices 0–113), not an out-of-range outline point. The glyph's action record references indices 117 and 116 for the bottom and top edges. The [ttfautohint source pinned by the Python wrapper](https://github.com/fonttools/ttfautohint/tree/eb64cdf2116a77b5091f1fe84a67abd051d362bc) skips CVT allocation for styles with zero regular blue zones ([allocation](https://github.com/fonttools/ttfautohint/blob/eb64cdf2116a77b5091f1fe84a67abd051d362bc/lib/tacvt.c#L101-L139)), yet Windows compatibility adds artificial ascent/descent alignment zones and its edge search still uses them ([edge search](https://github.com/fonttools/ttfautohint/blob/eb64cdf2116a77b5091f1fe84a67abd051d362bc/lib/talatin.c#L2583-L2597)). The backend debug trace identifies U+E0B0 as `none_dflt`, with its edges at −300 and 1,020 assigned to those two zones.

- In official hinted Regular, all 38 failing mappings are already present in the plain TTF at 12 ppem: U+2527, U+2580–U+2590, U+2594–U+259F and U+E0B0–U+E0B7. The set is unchanged through NF and NF-CN. For U+E0B0 specifically, a 1–256 ppem sweep failed at 1–200 and passed at 201–256. Non-pedantic FreeType returns success but substitutes zero for an out-of-range CVT read; all five Y coordinates become zero at 12 ppem, and the bitmap is 9×0. The initial per-process size sweep timed out; the single-process sweep completed.
- DirectWrite 10.0.26100.8875, Natural Symmetric grayscale and ClearType at 9/12/16 ppem, also produced abnormally low coverage with grid fitting enabled, rather than a blank mask in this setup. At 12 ppem, U+E0B0 grayscale coverage was 496 with grid fitting, versus 16,822 without it; the original plain, NF and rebuilt NF-CN gave the same readings.
- Rehinting the same plain Regular TTF with native ttfautohint 1.8.4.16-eb64 reproduced the failure with `windows_compatibility=True` regardless of the presence of a reference font. With `windows_compatibility=False`, U+E0B0 passed and all 38 baseline errors disappeared in a full cmap sweep at 12 ppem. Keeping Windows compatibility enabled but setting `fallback_script="none"` and `fallback_scaling=True` also cleared all 38 errors in the same test, kept the sampled digit's hints, and recovered the unhinted U+E0B0 grayscale coverage in DirectWrite. The follow-up below validates the latter workaround in the full static archive.

#### Powerline-fixed local static rebuild

The static base hinter now defaults to `fallback_scaling=True` while keeping `windows_compatibility=True`. With the default fallback script `none`, ttfautohint no longer emits glyph programs for that fallback category. The change is not limited to the 38 known failing characters.
